`@apexnative/navigation` gives a React Native app the navigation of the platform itself: the stacks, tabs, sheets and gestures of iOS and Android. You describe the screens and how they are arranged in TypeScript; the native side shows them and reports back.

```ts title="Navigation.ts"
import { createNavigation } from '@apexnative/navigation';
// your own components
import { Details, Home } from './src/screens';

export const Navigation = createNavigation({
  screens: { Home, Details },
  root: 'Home',
});
```

<DeviceVideo name="intro-hero" />

Home opens in a native stack. When Home calls `navigation.push('Details')`, Details slides in with the system transition, and the swipe back <Os name="iOS" /> or the back button <Os name="Android" /> returns to Home. The [Quick start](./quick-start) builds this app step by step.

:::info[Before 1.0]

The package is a pre-release: the banner at the top of each page says which one and how to install it, and the API can still change before 1.0.

:::

## Three ways to build navigation {#models}

Navigation for React Native is built in one of three ways. They answer two questions differently: <Mark>who owns the navigation state</Mark>, and <Mark>how your code speaks to it</Mark>.

All three can show native screens. The difference is not in how a screen is drawn, but in where the state lives, who decides what the user sees, and what your code has to say to change it.

## Describe, don't command {#describe}

When the platform owns the navigation, the app still has to speak to it. Commands with string ids and JSON layouts work, but every mistake in them shows up <Mark>at run time</Mark>: a wrong name, a missing prop, an id of a screen that is gone. The library keeps the native model and gives it a React API, so the same mistakes show up <Mark>in the editor</Mark>.

<Pair left="Commands by id" right="A typed description">

```js
navigator.push(screenId, {
  name: 'Details',
  props: { id: 42 },
});
```

```ts
const navigation = useNavigation();
navigation.push('Details', { props: { id: '42' } });
// 'Detail' or a missing id: a TypeScript error
```

</Pair>

## The platform already knows how to navigate {#platform}

<Os name="iOS" /> and <Os name="iPadOS" /> have `UINavigationController`, `UITabBarController`, sheets with detents and `UISplitViewController`. <Os name="Android" /> has its back stack, the back button and the Material components. Each of them holds years of decisions about <Mark>gestures, accessibility, layout on every screen size, memory and multitasking</Mark>.

A router that keeps its own model of the navigation has to mirror all of that into its state, and keep up with every release of the OS. The platform already does it. So the library gives React access to these containers instead of replacing them, and a new tab bar or toolbar of the OS arrives <Mark>with its beta</Mark>, not a year later.

:::note

The native look is a consequence, not the goal. The goal is native behavior: the same gestures, transitions, accessibility and memory use as in an app written in Swift or Kotlin.

:::

## How it works {#how}

The library has three layers. Your app describes the screens and the layout. A thin layer in JavaScript, the engine, turns that into commands. The platform does the navigation and sends events back.

## What it means for your code {#code}

Four habits follow from the model. Each of them comes from the same fact: the platform, not React, holds the screens.

- **Read the state, don't keep a copy.** The platform owns the stack, so a copy in React state goes stale after the first swipe back. Read it with [`useNavigationState`](../fundamentals/lifecycle-and-events#state), and listen to events instead of guessing.
- **One React root per screen, by default.** Each screen renders on its own, so a provider around one screen doesn't reach the others. Providers for the whole app or for every screen go to `createNavigation`; with `appProvider`, all screens share one React tree. More: [One tree](../architecture/one-tree#modes).
- **No safe area code.** Every screen keeps its content clear of the status bar, the cutout, the bars and the home indicator by itself, without `SafeAreaView` or a safe area library. The native side measures each screen, so the insets are right under a top bar, in a sheet and in a tab. More: [The safe area](../screen-ui/system-ui#safe-area).
- **Native screens are screens like the others.** A SwiftUI, UIKit or Compose screen is pushed, presented and put in tabs the same way as a React screen. More: [Native screens](../architecture/native-screens).
